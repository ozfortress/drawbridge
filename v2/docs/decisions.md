# Decisions

Implementation decisions and deviations from the plan. Newest first.

## P3 (2026-11-26)

- **The executor is a queue that reports, not a retry loop.** Todo 20's DiscordExecutor takes one catalogue op with its job id, lane and step seq, gates it behind the budgets and hands back the op's outcome or a taxonomy failure. A 429 is never retried in place: it comes back as a `rate_limited` failure carrying `retry_after` (action `pause_ratelimit`, attempts preserved, 02 §5.7) so the todo-17 engine path stays the single owner of `paused(ratelimit)`; the executor reacts with the 60-s halving, the per-bucket tally and the metrics hooks. The failure result carries `class` and `action` derived through `classifyError`/`isPermanentErrorClass` — no second copy of the §4.13 table — and the step executor (todo 25) feeds `signal` straight into `applyStepFailure`. Discord's own limits are never hardcoded (02 §4.4): discord.js's REST queues do the per-bucket pacing, the executor only reacts to 429 signals, and its own 2-per-guild and 10/s are options because the plan calls the starting values provisional.
- **The rate gate is spacing plus a rolling window, and a 429 re-arms rather than compounds.** No two dispatches closer than one rate interval (smooth pacing after idle) and never more than one effective rate's dispatches inside any rolling second — the stricter gate wins. Any 429 sets the halving window to half the base rate for 60 s from the moment the response landed; further 429s re-arm the window but never halve below half, and the rate restores the instant the window passes (pinned by exact dispatch-time assertions in the tests).
- **429 header fields ride the taxonomy signal.** `ApiErrorSignal` gained optional `bucket` and `rateLimitScope` (adapter-filled from `X-RateLimit-Bucket`/`X-RateLimit-Scope`): the executor records 429s by bucket and exempts shared-scope 429s from the invalid-request budget (02 §4.5). A 429 without a scope counts — Discord always sends the header, so an absent one is the adapter's conservatism, not Discord's word.
- **Preflight permissions are injected; hierarchy and capacity read the port.** The port cannot express the bot's own permission bits (`GuildRole` carries none), so the §4.2 names come from an injected provider with the bot's member id; the role-hierarchy rule (target strictly below the bot's top, managed roles untouchable) and the capacity margins read through `fetchGuildRoles`/`fetchGuildChannels`/`fetchMember`. Capacity reuses todo-8's `MAX_*` constants — discord-ops's first `@drawbridge/domain` dependency (runtime import, lockfile updated). Channel counts are a lower bound because obfuscated channels are invisible (02 §4.11); Discord's own 30013 is the backstop. A refusal never reaches Discord: it is reported as the code it stands in for (50013 permissions and hierarchy, 30005/30013 capacity), so `classifyError` maps it exactly like Discord's own answer and no invalid request is spent.
- **One alert per episode.** A 401 stops the executor once with exactly one alert; every queued write is refused with the same `fatal_config` failure and later writes fail fast without a port call (in-flight writes cannot be unsent). The invalid budget alerts once at 1000 inside the rolling 10 minutes and re-arms only after the window drains below the threshold, so a sustained breach is one alert and a fresh breach after the window slides is a new one.
- **The write path settles through a boundary catch.** Like the worker loop's `executeOneStep` (02 §3.2.2): a crash inside bookkeeping still settles the write through the taxonomy default instead of hanging the deferred, and the slot release in `.finally` keeps the queue moving. Hook failures are caught where the hooks are called; a failing metrics or alert sink is logged, never fatal.
- **FakeDiscord is test-local for todo 20.** The deterministic FakeScheduler plus a programmable fake port live in `packages/discord-ops/test/executor-helpers.ts`; the full FakeDiscord for the worker's adapter tests lands with the wiring (todo 25), where the plan's testkit row expects it.
- **The Discord port is plain data with zero module references.** `packages/discord-ops/src/port.ts` declares every shape locally — snowflakes as strings, permission bitfields as strings, ISO timestamps — and references no other module, so no discord.js or app type can cross the worker's REST boundary (02 §4.3); a test fails the build if a module reference sneaks in, and a compile-time probe pins the method surface to exactly the eighteen methods. The audit reason rides every create/update/delete call (02 §4.16); message sends and pins are not auditable creates, so they carry none. The five `fetch*` reads serve reconciliation (§5.6), the revert's human-message and empty-category checks (§5.9) and preflight; reads are not step ops and have no catalogue entries. Prior overwrites are captured through `fetchGuildChannels`, because the port deliberately has no single-channel read.
- **The catalogue's compensation vocabulary extends §5.9's five kinds.** Todo 19 requires every operation except the announcements (message send/pin, `reversible: false`, listed by `nonReversibleOps` for preview warnings) to carry a compensation, but §5.9's revert list names only delete role/channel/category, restore overwrites and delete DB rows. The catalogue therefore also declares restore descriptors (placement, name, member role) and best-effort recreations (role, channel, category) built from captured prior state; recreations are honest about loss — new snowflakes, no message history. `ENGINE_COMPENSATION_KINDS` marks the four the jobs revert engine executes today (typed as the engine's own Compensation union minus `delete_db_rows`), and the remaining kinds land with the step executor (todo 25): adopting them there is an engine change, deliberately not smuggled into this one. A test pins the four descriptors to jobs' Compensation shape so the vocabularies cannot drift apart.
- **discord-ops depends on jobs at the type level only.** `import type { Compensation, ExternalId, OverwriteSnapshot }` follows the plan's dependency direction (adapters implement ports that jobs define); the emitted dist references no other module at runtime, and tests pin the compatibility — `opReason` must equal the engine's `auditReasonTag`, and the four engine compensations must stay structurally identical. The correlation between one op's inputs, captured prior state and result is compile-time enforced by the kind-keyed `DiscordOpExecution` union (inputs at the top level, `kind` the direct discriminant — TypeScript does not narrow a parent by a nested discriminant), so a mismatched triple cannot be built and the builders need no runtime guards.
- **The scheduler stores recurrence in job rows, not a new table.** 02 §5.11 says scheduled jobs "use the same engine: `next_run_at`, lane `maintenance`", so each occurrence is an ordinary queued job whose `next_run_at` _is_ the schedule. A `runSchedulerTick` walks the registered operations and the active leagues, selects each operation's latest job in the league by `next_run_at`, and when no occurrence is in flight enqueues the next one with `next_run_at = anchor + interval` (a first occurrence is due immediately; an overdue anchor catches up at once, one occurrence at a time). The deterministic `sched:{type}:{leagueId}` plan hash makes the duplicate guard the concurrency arbiter — two racing ticks produce one row and the loser's `ConflictError` is a skip — and an `awaiting_decision` occurrence parks the schedule until an operator resolves it, because a broken operation must not re-run behind an unresolved decision. Active leagues only: widening to ended/archived leagues (retention, todo 52) is that operation's call.
- **The worker loop is a priority pipeline that executes one step per iteration.** Order: finish the worker's own in-flight running job (so a multi-step job runs at iteration speed instead of one step per lease expiry), reclaim an expired running lease (reconciling the mid-flight step first), claim a stalled revert, probe the oldest due `paused(external)` job — closing todo 17's gap where nothing enumerated the probes — then claim new work one lane at a time in 02 §4.4 order, closing todo 16's finding that a single multi-lane claim would let a high-priority `maintenance` job outrank an `interactive` one. A postponing probe falls through to claims; a resumed job executes its step in the same iteration; exactly one step executes per iteration under a 15-second lease heartbeat, then the loop yields and sleeps only when idle.
- **A transient failure's lease becomes the retry timer.** Todo 17 keeps a transient-failed job `running` with `next_run_at` at the backoff slot, but no scan polls a live-leased running job. The loop therefore sets `lease_expires_at` to the backoff moment: the existing `reclaimExpired` scan resumes the step exactly on time, with no new state, scan or timer.
- **Unexpected executor throws map through the taxonomy default.** A step error that is not a `DiscordOperationError` is an empty signal, and the taxonomy parks unrecognised failures in `awaiting_decision` (`invalid_input`) with the message as the named cause — the same rule the todo 17 classifier already applies to unmapped signals. The loop logs the failure and keeps looping (02 §3.2.2), and the worker role's placeholder executor uses the same path ("no step executor is wired yet") so an unexecutable job parks for an operator instead of being silently no-op'd as done.
- **Step success, the ledger and the completion move are two transactions.** The step's `done` status, its result, the external ids it created and their ledger rows commit together (02 §5.4); the completion move is a second transaction that re-locks the job and refuses cleanly if the job moved underneath — an operator's mid-step cancel keeps its decision while the step's writes and the ledger row stand, with a warn logged. A crash between the last step and the completion is recovered on reclaim: the loop completes a running job whose steps are all finished. `job.step.done` joins the engine's operation-log vocabulary.
- **The loop owns exactly two real timers; everything else is injected.** The idle wait is signal-aware (a shutdown never waits out an interval) and the heartbeat interval is the only other timer; the clock, the idle sleep and the jitter source are injected so tests drive iterations with a fake clock and no sleeps. A failing scheduler tick is caught, logged and backs off to the tick cadence instead of starving the claims below it — a misconfigured registry entry cannot brick the worker — and a signal stops the loop only after the current step is executed and persisted.
- **The worker's probe reads Postgres today; the Discord ports are placeholders.** The `paused(external)` cheap read (02 §5.7) is a real `select 1` on the worker's own database — one of the two external dependencies the plan names. The Citadel half of the probe, the step executor and the reconcile/revert adapters land with the Discord wiring (todo 25); until then the maintenance registry is empty and a claimed step parks rather than pretending to run.

- **`claimNext` never claims a `paused(external)` job.** 02 §5.7 lets an external pause resume only through a successful cheap-read probe, so the claim scan's paused filter excludes `pause_reason = 'external'` and `probePausedExternal` is the only way back to `running`. A paused(ratelimit|guild_unavailable) job stays claimable on its schedule. The probe's verdict (resume / postpone 30 s / escalate after 24 h) is a pure evaluator over an injected clock; a postponed probe writes no journal row, because one row every 30 seconds would flood the log. A successful probe hands the probing worker the lease without bumping the claim count.
- **The 24-hour external escalation window is measured from the journal, not a column.** The pause moment is the `at` of the job's latest `job.paused` row (reason `external`); when the row is missing (a trimmed journal) the probe falls back to "not yet 24 hours" and simply postpones. No schema change was needed.
- **A transient failure keeps the job `running` under its lease.** The plan's pause reasons are exactly external, ratelimit and guild_unavailable (02 §5.3); `transient` is not one of them, so a transient step failure records the step's attempt, pushes `next_run_at` to the next backoff slot (2 s doubling, ±20 % jitter, 5-minute cap, 6 attempts) and leaves the state alone — the worker waits out the schedule, and a crash mid-backoff is recovered by the existing lease reclaim. The sixth failed attempt moves the job to `failed`.
- **Decisions hand decided jobs back through the existing machinery, not a new state.** The machine has no `awaiting_decision -> queued` edge, and the claim scan covers `queued|paused` only, so a decided job re-enters execution as a `running` job whose lease is set to `now()`: the first `reclaimExpired` takes it over. A revert hands off the other way — the job stays `reverting` with no lease and `claimRevertNext` claims it.
- **`claimRevertNext` is the reverting-state twin of the claim scan (task-16 F3).** It locks `state = 'reverting'` jobs with `FOR UPDATE SKIP LOCKED`, requires `next_run_at` due and the lease free (freshly decided) or expired (a crashed revert worker), and sets a fresh 60-second lease. It deliberately does not route through `claimNext`'s `queued|paused` filter; `runRevert` then resumes at the first step that is still `done`, so a crashed compensation is never re-executed.
- **Compensation failures follow the plan's own pause split.** A rate-limited compensation postpones the rest of the revert by setting `next_run_at` to `retry_after` (the job stays `reverting`, attempts are not consumed) and `claimRevertNext` resumes on time. Every other §4.13 class parks the job in `awaiting_decision` — the machine's escape hatch out of `reverting` — with `decide_revert` as the way back. Non-Discord errors propagate: the per-compensation transaction rolled back, the lease will expire, and another worker retries.
- **Each compensation commits in its own transaction.** The port call, the step's `compensated` status, the ledger state (`deleted`/`archived` with its timestamp) and the journal row commit together, so a crash between compensations loses nothing; a crash after the Discord delete but before the commit re-runs the delete, which fails with `object_missing` and parks for an operator rather than destroying anything twice. A channel with human messages archives (warn row) and a non-empty category is left in place (the step stays `done`, warn row) — both are the plan's §5.9 rules.
- **The destructive gate for a revert is decided from the done steps' compensations.** `compensationDeletes` names the deleting kinds (role, channel, category, DB rows); a revert whose done steps carry any of them additionally requires `tournament.destructive`, checked at decision time before anything is written. A channel compensation counts as deleting even though it archives on human messages, because the decision is made before the message check runs. `delete_db_rows` executes through the revert port (the domain tables are not the job engine's to touch) while the engine updates its own ledger directly.
- **Unmapped Discord signals are permanent by default.** `classifyError` lets the 429 status and the §4.13 code table outrank everything else, and anything unrecognised (a bare 404, an empty signal) lands in `invalid_input` and parks the job: silently retrying an unclassified request is exactly what the taxonomy exists to prevent. A permanent class parks with a named cause in one machine row plus one engine `job.step.failure` row carrying the classified signal; `fatal_config` additionally opens an `alerts` row ("stop all writes", 02 §4.13) and `object_missing` marks the named ledger row `missing`.

- **Claims move jobs into `running` from `queued|paused` only.** The runnable-index decision below lists `reverting` as claimable, but the todo-15 transition table has no edge out of `reverting`, and compensations must keep running under that state until `finish_revert`. `claimNext` therefore filters to `queued|paused`; a crashed revert is picked up by the revert loop (a later engine todo) against the same index, which deliberately stays a superset.
- **Claim order is priority descending, then earliest due, then oldest.** The plan names the sort keys (priority, `next_run_at`, `created_at`) but not the direction of the integer `priority` column (default 0); larger values are treated as more urgent. The claim scan first reads up to 20 candidates unlocked and then re-locks them in order with `FOR UPDATE SKIP LOCKED`, re-checking the mutable predicates on the locked row, so a worker whose top candidate is taken walks down the list instead of returning empty.
- **The lease is a rolling window and cannot be resurrected.** A claim grants 60 seconds; each heartbeat sets `lease_expires_at = now() + 15 seconds` instead of adding to the remaining time, and the heartbeat predicate requires the lease to still be live and owned. A worker that lets its lease lapse loses ownership for good — even before any reclaimer arrives — so a reclaimer can never race a resurrected owner.
- **A renamed object asks for a decision; the ledger stays `live`.** 02 §5.6 prescribes `missing` for a recorded external id that is gone. When the object still exists under a different name, the job also parks in `awaiting_decision` (verification failed), but the ledger row is left alone: marking it missing could later drive a repair that duplicates the object. When every recorded id verifies, the step simply re-runs; create steps complete by name.
- **Reconciliation runs inside the reclaim row-lock transaction.** The port's reads happen while the job row is locked and before the lease moves, so two reclaimers cannot reconcile the same job concurrently; the lock is per-job and the port is two cheap reads. Adoption derives the ledger owner from the job (league when league-scoped, else guild); the step executor may refine the owner from step args later, and the todo-14 first-creator rule is preserved because the upsert never touches `created_by_job_id`.
- **`jobs_lease_idx` is `(lease_expires_at) where state = 'running'`.** The pre-recorded reclaim-index shape named `(state, lease_expires_at)`; the partial predicate already fixes the state, so the state key column is dropped as redundant. Migration `0003_mixed_cargill`.
- **The engine composes db repo writes through a widened handle.** `updateJobState`, `appendJobEvent`, `upsertDiscordObject` and `getDiscordObject` in `packages/db` now accept `Db | DbTx` (a widening; existing call sites unchanged), so claim and reclaim reuse the single write path per table inside their transactions. Lease arithmetic itself stays in `packages/jobs` with SQL `now()`, which the Date-typed repo patch cannot express. `enqueueJob` delegates to db `createJob`, which keeps the duplicate guard and its ConflictError mapping, and takes no advisory lock on purpose: enqueue must never wait behind a running job.
- **Engine journal codes for non-transitions.** Reclaim and reconciliation write `job.lease.reclaimed`, `job.reconcile.adopted` and `job.reconcile.rerun` rows; every state move still emits exactly the machine's row. This mirrors the todo-14 `step.*` precedent: the machine owns transitions, the engine owns operation log lines.
- **Runnable claim states are `queued|paused|reverting`.** The plan asks for a partial index on "runnable states" without listing them (`03` §2.4). The set comes from `02` §5.5-5.7 and §5.11: the claim scan polls `next_run_at` for queued jobs (scheduled ones included), paused jobs (ratelimit `retry_after`, external probes) and jobs mid-revert. `running` is reclaimed through `lease_expires_at` instead, `awaiting_decision` is human-gated and terminal states never run. Recorded beside `jobs_runnable_idx` in `packages/db/src/schema.ts`; a lease-reclaim scan would get its own partial index on `(state, lease_expires_at)` over `running`, not a wider runnable set.
- **No FKs from `jobs.guild_id` or `jobs.league_id`.** Jobs, steps and events are the durable journal (`02` §5.1, §5.13) and follow the `audit_log`/`alerts` precedent of plain domain id columns; an FK would either block `03` §1's hard-delete-with-audit-row rule or destroy journal history when a guild or league goes. The only job FKs are `job_steps.job_id` and `job_events.job_id` (cascade) plus `discord_objects.created_by_job_id` (set null), so step and event rows die with their job while ledger rows outlive it (`02` §5.9, A13).
- **The duplicate guard never rejects guild-scoped jobs.** `jobs_active_plan_key` is unique on `(league_id, plan_hash)` over the four active states, exactly as `03` §2.4 specifies; Postgres treats NULLs as distinct, so jobs with a NULL league are never deduplicated by it. If guild-scoped jobs should dedupe too, that is a plan-owner decision (a partial unique on `(guild_id, plan_hash)` would be the shape), not a silent schema change.
- **The ledger upsert keeps the first creator.** `upsertDiscordObject` updates state, kind, owner and verification fields on conflict but never `created_by_job_id`, so a later job re-creating an object cannot overwrite the original provenance. Revisit when reconciliation (`02` §5.6) starts adopting recreated objects.
- **The job state machine is pure and owns the event vocabulary.** `packages/jobs/src/state.ts` holds the states and pause reasons (`02` §5.3), the step statuses (`02` §5.4), the transition table with guards, and the `job_events` row (stable `code`, level, message, data) each move emits; `transition(job, event, ctx)` returns the row plus the next job fields and throws `InvalidTransition` on every illegal move. No clock, I/O or database: leases, claims, retries and probes stay with the engine tasks, which is what keeps the table exhaustively testable. `packages/db` `createJob` already writes the first `job.queued` row; its shape is kept identical here (`enqueueEvent`) so the engine can adopt one vocabulary without a format change.
- **Transition edges the plan does not spell out are derived from its rules.** `cancel` is legal from `queued|running|paused` (stop between steps and leave objects in place, like the §5.8 abort from `awaiting_decision`); `need_decision` from `paused` covers the external-probe escalation (§5.7) and from `reverting` covers a compensation hitting a §4.13 error, with `decide_revert` as the way back; `fail` from `running` is transient retries exhausted (§5.7). Terminal states have no exits: undoing a finished job means enqueuing a new one (A13), not reopening the row.

## P2 exit (2026-11-26)

- **Snowflakes have two independent guards.** The P2 exit failure probe (temporarily parsing Citadel bodies with `JSON.parse`) showed the zod schemas' `z.number().int()` safe-integer bound rejects float64-unsafe values at the parse boundary, so a lossy parser cannot store a corrupted snowflake: the preview fails closed (502 `citadel_invalid_response`) instead of writing a rounded id. The lossless parser keeps the exact string; the schema guard is the second defense. Both are now covered by the recorded exit evidence.
- **The P2-era decisions below held unchanged through the exit checks:** the `previews` table and `leagues.citadel_league_id` staying `integer` both ran green in the five recorded checks (golden equality, hidden league, injected 503, 18-digit round-trip, live manual run).

## P2 (2026-11-22)

- **`previews` table added to the schema.** Plan `03` §2.4 did not name it; the preview-and-approve flow needs the plan and its Citadel snapshot stored against a hash. Columns per todo 10: `id uuid pk`, `league_id` (fk, cascade), `created_by_user_id` (fk, set null, nullable like the other creator columns), `plan`/`snapshot` jsonb not null, `plan_hash` text not null, `citadel_snapshot_at`/`expires_at`/`consumed_at` nullable timestamptz (lifecycle set by the API, not defaulted), `created_at`; index `(league_id, created_at desc)`. Previews are deliberately not unique: re-previewing stores a new row and the API layer treats consumed or expired rows as unusable.
- **No `guilds.capture_all_text`.** A6 forbids capture-all; capture stays scoped to rows in `managed_channels` only.
- **`leagues.citadel_league_id` stays `integer`.** Citadel league ids are Rails serials, so integer is sufficient; changing it would churn the P1 unique key for no precision gain.

## P1 (2026-11-22)

- **Snowflakes as strings end to end.** Postgres columns are `numeric(20,0)` (not `bigint`) so drivers and JSON never round them. Drizzle returns strings; no `BigInt` conversion at boundaries.
- **Sessions are opaque tokens.** 256-bit random token in an `HttpOnly` cookie; only the SHA-256 hash is stored. Idle timeout 12 hours, absolute 7 days. Cookie name is `__Host-drawbridge_session` over HTTPS and `drawbridge_session` over plain HTTP, because `__Host-` requires `Secure` and local development runs on HTTP.
- **CSRF is double-submit.** A readable `drawbridge_csrf` cookie plus an `x-csrf-token` header, compared with a constant-time check. Applied by a global preHandler to mutating `/api/v1` routes.
- **OAuth is injected.** `createDiscordOAuth` takes `fetchImpl`, so tests assert the authorize URL, token body, Basic auth and bearer user lookup without network access. The web app accepts an injected `oauth` for the same reason.
- **Capability checks are pure.** `@drawbridge/authz` holds tiers, the capability catalogue, default league templates and the rank rules, with a matrix test. The web layer resolves them against the database.
- **Invite consumption promotes only.** An invite never demotes an existing tier, and it is consumed once inside a transaction; it also inserts league memberships from its grants.
- **Users are never reactivated by sign-in.** `upsertDiscordUser` updates profile and last login only. Disabled accounts stay disabled and are refused at the callback.
- **Migration workflow.** drizzle-kit generates SQL into `packages/db/drizzle`; the `migrate` role and `RUN_MODE=all` apply it. Migrations are committed. Only one agent may generate a migration at a time (see the handoff document).
- **Test database.** Integration tests use `TEST_DATABASE_URL` (defaults to the local compose database on port 5433), create `drawbridge_test` on demand, and truncate between tests. `fileParallelism` is off because the files share one database. Tests skip when Postgres is unreachable; CI provides a service.
- **CI.** The `checks` job now runs a Postgres 16 service and sets `TEST_DATABASE_URL`, so integration tests run in CI rather than skipping.
- **Panel styling is plain CSS for now.** The plan names Tailwind and shadcn; installing them was deferred to keep P1 focused on auth and data. Revisit before P4 when the panel grows. Recorded as a deviation.
- **Panel is optional at runtime.** `buildApp({ servePanel: false })` keeps API-only tests deterministic; production serves `apps/panel/dist` with an SPA fallback. There is exactly one `setNotFoundHandler`.
- **Fastify's own logger stays off.** All request logging goes through the redacting logger. Health probes are not logged as requests.
- **pnpm 12 uses `allowBuilds`.** `pnpm-workspace.yaml` allows the `esbuild` build (needed by drizzle-kit and Vite). Do not approve other build scripts without review.

## P0 (2026-11-21)

- **Node 24 LTS, pnpm 12 via corepack.** Pinned in `.nvmrc`, `engines` and `packageManager`. CI reads the same files.
- **TypeScript 7.0.2.** `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, ESM (`NodeNext`), project references, `tsc -b` at the root.
- **Vitest 5 with source aliases.** Tests import `@drawbridge/*` resolved to `src` (see `vitest.config.ts`), so `pnpm test` does not need a build first. Runtime in production uses built `dist`.
- **Biome 2.6** for lint and format. `noExplicitAny` and `noNonNullAssertion` are off. `noExplicitAny` must stay off only until the domain types land in P2.
- **Fastify 5.12** is the HTTP layer. Fastify's own logger is disabled; every request line goes through `@drawbridge/logging`, so redaction is uniform.
- **Own JSON logger instead of pino.** Requirements are JSON lines, levels, child bindings and redaction. A tiny implementation avoids a dependency and makes the `Secret` marker the primary mechanism. Two layers: `Secret` values print as `[secret]`, and sensitive key names (`token`, `secret`, `password`, `apikey`, `authorization`, `cookie`, `webhookurl`, ...) are redacted even for plain strings.
- **Config validation is strict.** `NODE_ENV=test` deliberately relaxes required secrets so CI can run without credentials. Every other mode fails fast with a list of field paths. `WEB_PORT` is coerced with integer bounds.
- **No `.env` loader dependency.** `pnpm dev:web` uses `node --env-file-if-exists=.env.local`. Deployed environments get real environment variables from Coolify.
- **Readiness is honest.** Until P3 the dependency list reports `postgres`, `s3` and `discord` as down but not required, so `/readyz` returns `degraded` (200) rather than a false `ok`. P1 makes `postgres` a real check.
- **Bot and worker idle instead of exiting.** They are stubs until P3. Exiting would cause restart loops in a supervisor.
- **One image, several roles.** `RUN_MODE` selects the role. `all` runs web, bot and worker in one process for development; production uses separate containers from the same image.
- **CI scope.** `.github/workflows/v2-ci.yml` triggers on `v2/**`, runs typecheck, lint, tests and build, then builds the Docker image without pushing.
